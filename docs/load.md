# Extract → Transform → Load

The quotation ETL now has one command that reads Excel, transforms into schema-v3
records, validates the complete batch, and loads PostgreSQL in one transaction.
You can also load a previously reviewed Transform JSON file without reading the
workbook again. Original Excel files are never saved or changed by the pipeline.

## Install and connect

From the repository root:

```bash
python -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Use PostgreSQL with the v3 schema. Integration checks ran on PostgreSQL 17.11.
The app uses `psycopg[binary]` 3.2.12, without requiring local libpq development
headers. Set `DATABASE_URL` through your secure environment configuration;
do not commit credentials. `--database-url-env NAME` selects a different binding.
No production database connection is assumed or required by the unit tests.

In this prepared cloud workspace, a local server is available on a private Unix
socket with peer authentication, no password, and TCP disabled. Its helper scripts
and data live outside the checkout. To start it again after a machine restart:

```bash
bash /workspace/onboarding/marine-sales/postgres-start.sh
export DATABASE_URL="postgresql://$(id -un)@/marine_sales?host=/workspace/.services/marine-sales-postgres/socket&port=55432"
```

These helpers are cloud setup artifacts, not part of the Git repository. Other
machines should use their own PostgreSQL installation and connection binding.
The saved cloud setup installs local Debian PostgreSQL tools with normal TLS,
archive signature, and package checksum verification. It does not install into
the operating system or expose the server over TCP.

## Review first, then load

Perform Extract, Transform and Load validation without opening a database:

```bash
.venv/bin/python -m etl.pipeline data/raw/quotations.xlsx \
  --sheet 'exact-quotation-sheet' --dry-run \
  --report data/processed/review.json
```

Create schema v3 in a new dedicated schema and load a reviewed quotation:

```bash
.venv/bin/python -m etl.pipeline data/raw/quotations.xlsx \
  --sheet 'exact-quotation-sheet' --schema marine \
  --init-schema --report data/processed/first-load.json
```

`--init-schema` is explicit and non-destructive: it creates tables using the
unchanged `database/schema_v3.sql`, or verifies an already initialized schema.
It refuses unrelated/partial schemas, does not drop or migrate existing tables,
and checks required column types, generated IDs, primary/foreign keys, required
NOT NULL columns and the unique quotation reference. Initialization is a separate
transaction: an empty initialized schema can remain if the later data load fails.

Reuse a staging JSON generated by `python -m etl.transform`:

```bash
.venv/bin/python -m etl.load data/processed/quotations.transformed.json \
  --schema marine --report data/processed/json-load.json
```

Omitting `--sheet` processes detected M/O quotation sheets. Support document
association remains explicit; select exactly one quotation with `--kit-sheet`
and/or `--cost-sheet`. The pipeline supports the same currency and supporting
sheet flags as [Transform](transform.md). File names and sheet order never establish
KIT/quotation or KIT/item relationships.

## Validation and repeat runs

- The entire batch is checked before any data writes. Required values, enums,
  reference segments, Decimal ranges/precision, dates, integer quantities, nested
  relationships and Transform issues are checked independently of `is_valid`.
  Generated database IDs cannot be provided in staging rows.
- Errors always reject a record. Warnings block loading by default. After reviewing
  the source and report, `--allow-warnings` permits warning-only records; it never
  permits validation errors. Unknown or per-vessel aggregate totals remain NULL.
- Duplicate references inside one batch reject **every copy**, including an
  invalid copy. Select the intended source explicitly; later rows never win
  silently. Suffixes remain part of the complete unique quotation reference.
- By default, any rejected record blocks the entire batch. `--skip-invalid`
  explicitly excludes rejected records and loads the accepted remainder in one
  transaction. Rejections and original record indices are retained in the report.
- Existing references default to `--on-existing skip`: the current stored quote
  and all master/child rows remain untouched. Changed source data is still skipped
  under this policy, so the outcome is reported as skipped, not updated.
- `--on-existing error` aborts the accepted batch if an existing reference is found.
  `--on-existing replace` explicitly updates the quotation while preserving its
  ID, then replaces only its own items, vessel links, service details and supporting
  documents. Master rows remain. Cross-quotation KIT-item dependencies block
  replacement rather than silently modifying another quotation.
- SQL failures roll back the batch, including earlier rows and newly created
  masters. If a connection is lost during commit, verify database state before
  retrying; the default skip policy prevents a repeated reference from duplicating.

The result distinguishes `inserted`, `skipped`, `replaced` and `rejected`. A
successful dry run checks source data only; it does not prove connectivity, schema
compatibility, permissions or the absence of existing database master duplicates.

## Master matching and relationships

PostgreSQL generates all primary keys. Load inserts parents before children and
uses their actual returned IDs for foreign keys. No placeholder IDs are created.
Optional missing contacts, service scopes and KIT documents receive no rows.
Component prices, group subtotals and displayed final amounts are retained.

Matching is deliberately exact: customer name; contact customer/name/phone/email;
vessel customer/name/hull. NULLs match NULLs with `IS NOT DISTINCT FROM`. No fuzzy
customer merging, spelling correction, vessel ownership inference, or master
equipment updates occur. More than one existing candidate aborts the batch.
KIT Detail and Cost Sheet remain separate, and `kit_quotation_item_id` stays NULL
because Transform does not currently establish a reliable item association.

A transaction advisory lock serializes this loader in each database/schema with
READ COMMITTED isolation. This prevents competing instances of this loader from
inserting the same master while one is in flight. The v3 schema has no unique
customer/contact/vessel natural-key constraints; unrelated writers must coordinate
or add a separately reviewed migration. Their changes are not automatically merged.

## Reports and exit status

Reports contain the complete Transform staging data, validation results and load
outcomes. They include private business information; use ignored `data/processed`
paths and do not commit them. Connection strings/passwords are not written to
reports or printed. Reports are created exclusively and never overwrite source
or existing files.

| Exit | Meaning |
|---|---|
| 0 | All selected records accepted; load committed, or dry run passed. Existing skips are reported. |
| 1 | Validation rejected records. With `--skip-invalid`, accepted records can still have committed. |
| 2 | Input, configuration, connection, schema or transaction failure. Check report/DB state before retrying. |

The local JSON report and PostgreSQL commit are not a distributed transaction.
Report creation is checked before loading, but a disk failure after a database
commit can still prevent final report writing. A production audit/outbox mechanism,
scheduling, incremental source discovery and database backups are future features.

## Python API

```python
import psycopg
from etl.load import initialize_schema, load_records

with psycopg.connect(database_url, autocommit=True) as connection:
    initialize_schema(connection, schema="marine")  # explicit, when needed
    report = load_records(connection, transformed_records, schema="marine")
```

Pass an idle connection. Load owns its batch transaction and refuses an already
active caller transaction rather than committing someone else's work.

## Tests

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
```

Set `MARINE_TEST_DATABASE_URL` to a dedicated test PostgreSQL database to run the
real integration suite. It creates/drops only unique `test_load_*` schemas that
belong to the run. Without that variable, PostgreSQL tests are explicitly skipped;
unit tests passing alone do not verify database loading.

```bash
export MARINE_TEST_DATABASE_URL="$DATABASE_URL"
.venv/bin/python -m unittest discover -s tests -p 'test_*.py' -v
```

Tests cover the full FK graph, monetary precision, exact matching, repeated loads,
explicit replacement, source validation, concurrency, SQL literal handling,
schema compatibility and rollback after a forced failure partway through a batch.
